先看这五句 / Highlights

译者补充，不是原文。

  1. 现有 Claude Fable 5 提示词在 5.1 上通常不用改；真正要动的，是你已经观察到的那几条行为差异。
  2. effort 是主旋钮：默认 high，用自己的 evals 把 low / medium / xhigh / max 重新扫一遍，档位名在不同模型上不是同一份思考量。
  3. 对话历史只追加：assistant 回合连 thinking 块原样回传；改前缀会 400（bound to a different conversation）或丢掉推理。
  4. 智能体循环里三件事：打开进度更新、同一回合批量互不依赖的工具调用、别把「下一步」说完就收工。
  5. low 更爱凭记忆作答；xhigh / max 会长考；安全分类器仍可能返回 stop_reason: "refusal"。

症状索引

模型能力、API 变更、定价与可用性，见Claude Fable 5.1 有什么新变化。跨 Claude 模型通用的技巧，见提示词最佳实践。

你现有的 Claude Fable 5 提示词在 Claude Fable 5.1 上通常不用改也能表现很好，但有几处行为差异值得知道。从与你观察到的现象对应的章节开始：

  • 拿不准该跑哪档 effort，或延迟和成本高于任务所需：考虑所有 effort 档位
  • 工具调用之间几乎没有文字：要求面向用户的进度更新
  • 智能体循环里每回合只调一次工具：在智能体循环里批量独立工具调用
  • 请求失败，报 bound to a different conversation，或你的 harness 会在请求之间改写更早的回合：对话历史只追加、不改写
  • 散文又长又密：文风密度
  • 聊天回复的结构不够用：聊天里的格式
  • 摘要复述了原文措辞却没标成引用：引用检索到的来源
  • 回合在工作做完前就结束，或模型为你已经要求过的工作再问许可：把整件任务做完
  • 客户端压缩摘要丢掉了约束、决策或精确细节：告诉模型压缩摘要必须保留什么
  • 未经请求的修复或扩展，或提交的测试文件比任务需要的多：改动和测试只做任务要求的
  • 低 effort 下凭记忆作答而不搜索：低 effort 下的搜索触发
  • 无害的编码请求返回 stop_reason: "refusal"：减少安全分类器误拒
  • 为了小改动重写整个文件：优先针对性编辑，不要整文件重写
  • xhigh 或 max 下的长交付很慢，或撞上 max_tokens：在 xhigh 和 max 给长输出留空间
  • 主智能体在子智能体运行时闲着：让主智能体在子智能体运行时继续干活
  • 关于图表和稠密图像的答案漏掉细节：给视觉任务裁剪和放大工具

Claude Fable 5.1 会运行安全分类器，并可能返回 stop_reason: "refusal"。见拒绝、回退与计费以及减少安全分类器误拒。

考虑所有 effort 档位

从默认 effort 档位 high 开始，再用你自己的 evals 测其余档位（low、medium、xhigh 和 max）。在 Claude Fable 5.1 上，effort 是在智力、延迟和成本之间做取舍的主控。即便你已经在 Claude Fable 5 上扫过一遍，也要重新扫：档位名称在不同模型上并不对应同样多的思考量。

Claude Fable 5.1 相对 Claude Fable 5 的能力提升在各档位都有，在更高档位上最大。在 medium，结果大致赶上 Claude Fable 5，成本却更低，所以只要 evals 显示质量站得住，就降到 medium 或 low。在 low，Claude Fable 5.1 按每次任务成本常常能和 Claude Opus、Claude Sonnet 模型竞争，分数还更高，所以你本来会用更小模型配更高 effort 的地方，把 low 也放进对比。

两个与档位相关的行为有独立章节：在 low，Claude Fable 5.1 更少调用搜索和检索工具（见低 effort 下的搜索触发）；在 xhigh 和 max，它可能在写出长交付之前思考更久（见在 xhigh 和 max 给长输出留空间）。

要求面向用户的进度更新

Claude Fable 5.1 的默认行为，是在长工具调用回合里比 Claude Fable 5 写更少面向用户的更新。effort 越高、工具链越长，这一点越明显。用户会看到智能体连续安静好几分钟，或者最后一条消息只覆盖最后一步，而不是整件任务。

首先，确认你的客户端到底有没有收到进度更新。模型在工具调用之间写下的短注——刚找到什么、接下来做什么——会作为进度更新 thinking 块返回；在默认的 thinking.display 为 "omitted" 时，这些块是空的。把 display: "updates" 打开（beta，请求头 thinking-display-updates-2026-08-18），并把每个非空 thinking 块渲染成状态行；或者设 "summarized"，连同摘要后的推理一起接收。如果你根本没请求它们，模型的更新可能只是没到达用户。

其次，检查提示词里有没有压住叙述的指令。更早的模型工作时很爱给更新，于是系统提示里会出现「把所有发现留到最终回复」这类句子。加新内容之前，先删掉这类句子。

如果你仍想要更多更新，例如结对编程或其他人在回路里的工作，加一句短的系统提示，说明你希望模型何时给出面向用户的文字、每条更新该包含什么：

开工前说一句你要做什么；过程中给短更新；收尾给一份独立可读的复盘。提示词原文保留英文，便于直接粘贴。

Before you start, say in a line what you're about to do; brief updates while you work help the user follow along. Close with a short recap that stands on its own — what you found, what you did, and what's next — so a reader who only sees the last message has the full picture.

如果你的产品会折叠或隐藏工具输出，告诉模型。否则它可能跑一些命令去「展示」用户其实永远看不到的输出。把这条说明放在回合级 system 消息里（clear_at: "next_user_message"，beta）：

用户几乎看不到命令输出时，该让用户读的内容写进回复。

Only you see that command's output — the user's terminal shows at most a few lines of it. If the user needs to read any of it, put it in your reply.

在智能体循环里批量独立工具调用

Claude Fable 5.1 通常会按预期发出并行工具调用：当请求点名要取好几样东西时，它会并行发出这些调用。例外是编码和计算机使用循环——下一步的独立调用是由任务暗示的，而不是被明确点名（自定义编码智能体、bash 加编辑器 harness、computer use）：这时它可能改成每回合只发一次。这不影响答案质量，但每个多余回合都要花 token、一次往返和墙上时钟。在当前请求末尾加一句提醒就能处理：

先私下列出下一步需要什么，再在同一轮请求所有互不依赖的项。

First privately list what you need next; then request every item that doesn't depend on another's result in this one response.

每次把工具结果送回去时，把它追加在那条 user 消息之后，作为一条回合级 system 消息：messages 里一条 role: "system" 记录，带 clear_at: "next_user_message"。一旦后面出现更新的 user 消息，API 会清掉更早的副本，于是模型只读到最新的那条。回合级 system 消息处于 beta，需要 beta 请求头 mid-conversation-system-clear-at-2026-08-21。没有 beta 时，把这句话放在同一条 user 消息里、tool_result 块后面的文本块中。

每一回合都追加一份新副本，更早的副本原封不动留在原地，字节级一致。它们还在数组里，但一旦被清除，模型就看不到它们，也不消耗输入 token。删除或改写它们等于编辑更早的回合：会从那一点重启提示词缓存，并使它们之后的 thinking 块失效（见对话历史只追加、不改写）。

下面的循环展示这种放置方式。每个 assistant 回合按返回原样回传，每个 user 回合只携带工具结果，后面跟一份新的回合级提醒副本。

    break;

  for (const block of response.content) {
    if (block.type !== "tool_use") {
      continue;
    }
    const { input } = block;
    const path =
      typeof input === "object" &&
      input !== null &&
      "path" in input &&
      typeof input.path === "string"
        ? input.path
        : "";
    const text = FILES.get(path);
    if (text === undefined) {
      toolResults.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: `File not found: ${path}`,
        is_error: true,
      });
      continue;
    }
    toolResults.push({
      type: "tool_result",
      tool_use_id: block.id,
      content: text,
    });
  }
  // Send the tool results as the user turn, then a fresh copy of the nudge as a
  // turn-scoped system message. Leave earlier copies in place: the API clears them,
  // so the model sees only the newest one.
  messages.push({ role: "user", content: toolResults });
  messages.push({
    role: "system",
    content: BATCH_NUDGE,
    clear_at: "next_user_message",
  });
}

const finalText = response.content.find((block) => block.type === "text");

                    ToolUseID = toolUse.ID,
                    Content = $"File not found: {path}",

            }

package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/anthropics/anthropic-sdk-go"
)

const batchNudge = "First privately list what you need next; then request every item " +
	"that doesn't depend on another's result in this one response."

// In-memory files stand in for a working directory so the sample runs anywhere.
var files = map[string]string{
	"pyproject.toml": `[project]
name = "demo"
version = "0.1.0"
description = "Demo project for the batching example"
`,
	"README.md": `# demo

A small demo project. Run "demo --help" for usage.
`,
}

func main() {
	client := anthropic.NewClient()
	ctx := context.Background()

	tools := []anthropic.BetaToolUnionParam{
		{OfTool: &anthropic.BetaToolParam{
			Name:        "read_file",
			Description: anthropic.String("Read a UTF-8 text file from the working directory."),
			InputSchema: anthropic.BetaToolInputSchemaParam{
				Properties: map[string]any{
					"path": map[string]any{"type": "string"},
				},
				Required: []string{"path"},
			},
		}},
	}
	messages := []anthropic.BetaMessageParam{
		anthropic.NewBetaUserMessage(anthropic.NewBetaTextBlock("Summarize pyproject.toml and README.md.")),
	}

	var response *anthropic.BetaMessage
	for {
		var err error
		response, err = client.Beta.Messages.New(ctx, anthropic.BetaMessageNewParams{
			Model:     "claude-fable-5-1",
			MaxTokens: 16000,
			Betas:     []anthropic.AnthropicBeta{"mid-conversation-system-clear-at-2026-08-21"},
			Tools:     tools,
			Messages:  messages,
		})
		if err != nil {
			log.Fatal(err)
		}
		// Append the assistant turn exactly as returned, thinking blocks included.
		messages = append(messages, response.ToParam())
		if response.StopReason != anthropic.BetaStopReasonToolUse {
			break
		}
		var toolResults []anthropic.BetaContentBlockParamUnion
		for _, block := range response.Content {
			toolUse, ok := block.AsAny().(anthropic.BetaToolUseBlock)
			if !ok {
				continue
			}
			var input struct {
				Path string `json:"path"`
			}
			if err := json.Unmarshal([]byte(toolUse.JSON.Input.Raw()), &input); err != nil {
				log.Fatal(err)
			}
			text, found := files[input.Path]
			if !found {
				text = "File not found: " + input.Path
			}
			toolResults = append(toolResults, anthropic.NewBetaToolResultBlock(toolUse.ID, text, !found))
		}
		// Send the tool results as the user turn, then a fresh copy of the nudge as a
		// turn-scoped system message. Leave earlier copies in place: the API clears them,
		// so the model sees only the newest one.
		messages = append(messages, anthropic.NewBetaUserMessage(toolResults...))
		messages = append(messages, anthropic.BetaMessageParam{
			Role:    anthropic.BetaMessageParamRoleSystem,
			Content: []anthropic.BetaContentBlockParamUnion{anthropic.NewBetaTextBlock(batchNudge)},
			ClearAt: anthropic.BetaMessageParamClearAtNextUserMessage,
		})
	}

	for _, block := range response.Content {
		if textBlock, ok := block.AsAny().(anthropic.BetaTextBlock); ok {
			fmt.Println(textBlock.Text)
			break
		}
	}
}

            .role(BetaMessageParam.Role.SYSTEM)
            .content(BATCH_NUDGE)
            .clearAt(BetaMessageParam.ClearAt.NEXT_USER_MESSAGE)
            .build());
    }

    String finalText = response.content().stream()
        .flatMap(block -> block.text().stream())
        .findFirst()
        .orElseThrow()

对话历史只追加、不改写

把每个 assistant 回合按 API 返回的原样追加进历史，包括 thinking 块，并且不要在请求之间编辑更早的回合。对 2026 年 8 月 31 日及之后创建的新账户，Claude Fable 5.1 的 thinking 块只在产生它们的那次精确对话里有效：如果重放某个 thinking 块时，它前面的前缀（系统提示、工具列表，或任何更早的消息）已经变了，请求会返回 400；或者，若你设置 thinking.block_binding.prefix_mismatch_behavior: "drop_block"（beta，请求头 thinking-binding-controls-2026-08-01），受影响的块会被丢掉。未来模型预计会对所有账户执行这项检查，所以即便你今天还没被强制，现在就养成这个模式。

会触发这项检查的历史编辑，也正是会重启提示词缓存的那些：注入再删掉每回合提醒、就地摘要更早的回合，或在会话中途改写系统提示。把每回合提醒做成回合级 system 消息；用一条会话中途的 system 消息来改指令或工具，而不是重写 system 或 tools；修剪交给服务端压缩或上下文编辑。若你在客户端压缩，最简单的形状是：用一条摘要消息加上新的 user 回合替换整段历史，其它什么都不重放——没有 thinking 块被带过去，所以不会失败，模型会在压缩后的对话上重新思考（见客户端自定义压缩）。因为缓存读取现在更便宜（见定价），为省钱而过早压缩，在 Claude Fable 5.1 上可能不再是正确的成本—智力权衡，所以试试更晚的压缩点。

要找出 harness 已经在做的编辑，用 prefix_mismatch_behavior: "drop_block" 跑一次会话并记录 input_transformations，做法见如何判断你的集成是否受影响；或者抓取它在几个正常回合里发出的精确请求，确认连续请求在追加的回合之前是字节级相同的。

文风密度

Claude Fable 5.1 的写作整体比更早的 Claude 模型高一档，套话更少，没解释的行话也更少。但有些情况下，它的散文比 Claude Fable 5 更密：句子更长，段落间断更少。一条定义反面模式——做作文风——的指令会有帮助。加到 user 消息里（首选）或系统提示里：

Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it.

短版本往往也够用：

短指令：去掉所有做作文风。

Please remove all mannered prose.

把整件任务做完

Claude Fable 5.1 能在方法论上几乎不需要指导的情况下执行非常长的任务，尤其当目标清楚时。但在复杂的异步工作负载上，要提醒它不要在工作做完前结束回合。没有这句提醒，模型有时会描述下一步要做什么而不是去做（「Next, I'll …」），或停下来为原始请求已经覆盖的步骤征求许可（「Shall I apply this?」）。用户只好回复「continue」或「go ahead」，这适合结对编程和其他人在回路里的工作，但没有用上模型完整的长程能力。

两条系统提示加在一起可以缓解。两条都用。若必须限制提示长度，只用第一条，它保留了大部分效果。第一条告诉模型：不要为已经要求过的工作再发问，并执行它已经说出口的下一步：

自主执行：用户不在实时盯着；可逆且属于原请求的动作直接做；最后一段如果还是计划或「我会…」，现在就用工具做完。

You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking 'Want me to…?' or 'Shall I…?' will block the work. For reversible actions that follow from the original request, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Offering follow-ups after the task is done is fine; asking permission before doing the work is not.

Exception: when the user is describing a problem, asking a question, or thinking out loud rather than requesting a change, the deliverable is your assessment. Report your findings and stop. Don't apply a fix until they ask for one.

Before ending your turn, check your last paragraph. If it is a plan, an analysis, a question, a list of next steps, or a promise about work you have not done ('I'll…', 'let me know when…'), do that work now with tool calls. That includes retrying after errors and gathering missing information yourself. Do not stop because the context or session is long. End your turn only when the task is complete or you are blocked on input only the user can provide.

Before running a command that changes system state (such as restarts, deletes, or config edits), check that the evidence actually supports that specific action. A signal that pattern-matches to a known failure may have a different cause.

开场那句——告诉模型用户并不在看——承担了大部分效果。按原文保留。如果你的产品需要模型为特定确认停下来，在这句后面加一句，把它们列出来。这段也可能让模型更少为含糊请求发问，所以在你自己的任务上核对这一权衡。

第二条把用户的请求定义为交付范围：

用户请求（或他们批准的计划）就是范围，范围就是交付物：不要悄悄缩小、扩大或替换。

# Delivering work
The user's request — or the plan they approved — sets the scope, and the scope is the deliverable: don't quietly narrow, widen, or swap it. Read ambiguity the way a careful colleague would: make routine judgment calls yourself, and check in only when different readings would lead to materially different work. If you see a real problem with the task as specified, say so in a sentence or two and keep building under stated assumptions; if the user hears the concern and reaffirms, that is their decision, so deliver the full request.

If a question comes up partway, first do everything that doesn't depend on the answer; then state the assumption you made, or — when going ahead on a wrong guess would be unsafe or would make the work useless — put the question at the end of a turn that also delivers that progress. If one part turns out to be blocked, complete every other part in full and say exactly what you left out and why — the whole task is the deliverable, and scaling it down is the user's call, not yours. A step you have decided on is something to run, not to announce: describing the next step and ending the turn leaves it undone until the user replies.

Keep changes to what the request needs. Something else you notice worth doing — cleanup or documentation the task didn't call for, a change to a file the task didn't require — is a suggestion to make at the end, not a change to make; actions clearly beyond what the ask implies, and risky or destructive ones, still need the user's go-ahead.

告诉模型压缩摘要必须保留什么

当一段长对话被压缩时，明确告诉 Claude Fable 5.1 摘要必须保留什么，它会反应很好。服务端压缩已经在做这件事。若你在客户端压缩，用下面这条摘要指令：

摘要须原样保留约束、决定、难复原的细节和未决事项；用户原话靠近原文，模型自己的解释可以压得更短。

Summarize the transcript inside <summary></summary> tags. Include relevant information in the summary such that this conversation will be continued by a new context window without needing to redo work or be reprovided with relevant constraints or context. Be sure to preserve: (1) any difficulties or problems that came up, and how they were handled or resolved; (2) any possibilities, options, or approaches that were raised, tried, or set aside, and why; (3) anything that was asked for, decided, agreed, ruled out, or established as a preference, constraint, or boundary — stated exactly; (4) exactly where things stand now — what has been covered, settled, or completed so far; (5) anything still open, unresolved, promised, or expected to happen next; (6) specific details that would be hard to reconstruct — names, numbers, dates, exact wording, links or references — kept exactly. Be complete on these even at the cost of length; keep everything else concise. Weight the two voices differently: keep what the user said, asked for, shared, or established carefully and close to their own words; your own explanations and reasoning can be condensed much further, to what they concluded or produced — as long as nothing in the six items above is dropped.

改动和测试只做任务要求的

当被要求实现一个开放式功能时，Claude Fable 5.1 会交付被要求的东西，有时还会多做：它可能修附近的代码、扩展任务没提到的行为，或提交比这次改动所值更多的测试文件。关于什么不要做的明确指令，它会反应很好。加上下面这条指令后，未经请求的添加和被提交的测试代码会大幅下降，任务成功率没有可测的变化：

任务没点名的 bug / 优化 / 扩展不要塞进这次改动；测试只在任务要求或仓库已有同类测试时提交。

If, while working or testing, you find a pre-existing bug, a performance concern, or behavior the task doesn't mention, don't fix, optimize or extend it in this change unless the requested behavior cannot work without it; report it as a follow-up in your summary. Where the task is ambiguous, implement the reading its wording and the surrounding code most directly support, state that assumption in your summary, and don't build for the other readings as well. Verify your work however you like; scratch scripts and quick checks need not be kept. Commit tests only where the task asks for them or this repository already keeps tests for this kind of change, sized like the neighboring test files — roughly one focused test per stated behavior — and don't turn scratch checks into additional permanent test files. This is about extras only: implement every behavior the task asks for, completely.

低 effort 下的搜索触发

在 low effort 下，Claude Fable 5.1 比 Claude Fable 5 更少调用搜索或检索工具，更常凭记忆作答。有些情况下，最简单的修复是只把受影响的回合提高 effort，而不是整段对话。见在对话中途更改 effort。

另一些情况下，朝核实方向推一把提示词会有帮助。在系统提示里说明：认出一个名字并不等于知道它的当前状态，这类名字应按用户写下的样子去搜：

对认不准、或处于快速变化领域的名字，先搜再答；至少一条查询带上用户原词。熟悉不是跳过搜索的理由。

When a query centers on a name you do not confidently recognize, or recognize from a fast-moving area like AI models and developer tools where the landscape shifts within months, the name itself is the thing to verify: search before answering, and include the name as the user wrote it in at least one query alongside any reformulations. This holds even when you have some background on it — partial background is exactly what makes an out-of-date answer sound authoritative, so familiarity is not a reason to skip the search.

减少安全分类器误拒

Claude Fable 5.1 的安全分类器比 Claude Fable 5 刚发布时更少误报，并且在源代码里找漏洞是允许的。误报仍会发生，被拦住的请求返回 stop_reason: "refusal"（见拒绝、回退与计费）。三种情形更容易触发：

  • 编译检查式措辞：不要问「Does this program compile without errors?」，改问「Are there any bugs in this program?」
  • 较少人知道的编程语言：给模型关于这门语言是什么、怎么工作的上下文，例如让它能读到该语言的文档。
  • 工具输出里的 Base64：把 base64 编码数据送进模型上下文的工具可能触发误报，建议的修复是去掉它们。

优先针对性编辑，不要整文件重写

如果 Claude Fable 5.1 为了小改动重写整个文件，把下面这条指令追加到系统提示或第一条 user 消息。Claude Fable 5.1 比 Claude Fable 5 更常重写整个文本文件，而不是做针对性编辑。结果文件通常一样，但除非文件很短或大部分都在变，重写会消耗更多输出 token 和时间。这条指令能让 Claude Fable 5.1 在中小改动上回到与 Claude Fable 5 一致。

在不影响最终结果的前提下，尽量外科手术式编辑，而不是重写整份文件。

The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing.

在 xhigh 和 max 给长输出留空间

在 xhigh，尤其是 max effort 下，Claude Fable 5.1 可能在开始写回复之前思考更久。当单次请求要求一份长交付，例如完整重写一份长文档，它可能在思考里先起草大部分交付，再作为回复再写一遍，于是等待更长、输出 token 更多。最简单的做法是把这类请求跑在 high——推荐的起点——只在你测到质量收益的地方再升到 xhigh 或 max（见考虑所有 effort 档位）。若你确实在 xhigh 或 max 上跑它们：

  • 把 max_tokens 设得给思考和回复都留出空间，而不只是你预期的回复长度。
  • 把下面这条注记追加到 user 消息末尾。它会让散文和代码请求上的思考短得多。把 [max_tokens] 换成该请求实际的 max_tokens 值，例如 64,000。

思考里的起草和回复共用同一个 token 上限；长交付不要在推理里先写全文，再在回复里写第二遍。

Everything produced in one reply, including any reasoning or drafting it does before the reply, counts toward a single limit of about [max_tokens] tokens. If that limit is reached before the reply is finished, the person receives a cut-off response and has to start over. Composing an entire output or deliverable in full as reasoning and then again as a reply would double the length of the turn without improving the result, so don't do that.

Instead, when the person has asked for a long or effort-intensive deliverable such as a multi-section document, a large table or dataset, or a complete code file, spend extra effort on understanding the request, checking the inputs the answer depends on, settling the structure and other difficult decisions, and otherwise using the reasoning space to reason and the output space to write an output. Usually it is not needed to draft an output multiple times.

让主智能体在子智能体运行时继续干活

如果你的编码智能体允许 Claude Fable 5.1 把工作委派给子智能体，不要强迫主智能体为每一个停下来等待。在编码任务上，让主智能体在子智能体运行时继续干，能在质量、token 用量和成本相近的情况下降低平均完成时间。这样设置：

  • 启动子智能体的工具立即返回。
  • 每个子智能体的结果就绪后，再在后面的 user 消息里传回给主智能体。
  • 给主智能体一个它可以在想等待结果时调用的单独工具。

模型仍然经常选择等待。时间节省来自那些它转去干别的工作的运行。

给视觉任务裁剪和放大工具

Claude Fable 5.1 开箱的视觉能力更好；在稠密图表这类复杂视觉输入上，当它可以迭代地分析、裁剪并在视觉上核验所见时，才做得最好。要拿到完整收益，把模型当智能体来跑，并给它一个容器：里面放原始图像或视频，并预装基本图像处理库（例如 PIL 和 OpenCV）。如果跑容器开销太大，单是一个图像裁剪工具就能拿到大部分提升：一个返回所选区域、裁切并放大后的工具，让模型能更深入地查看特定细节，并用图像 token 扩展测试时计算。裁剪工具配方里有一份可工作的定义。
